## 1. max-model-len

### 📌 作用

**单个请求的最大序列长度**（包括 prompt 和生成的 token 总数）。

### 🔧 配置方式

```bash
# 使用模型默认值
vllm serve model_name

# 手动指定为 32K
vllm serve model_name --max-model-len 32768

# 使用人类可读格式
vllm serve model_name --max-model-len 32k   # 32000
vllm serve model_name --max-model-len 32K   # 32768
```

### 🎯 自动推导逻辑

如果不指定，vLLM 会按以下优先级从模型配置中自动推导：

1. **检查配置键**（按优先级排序）：
   - `max_position_embeddings` (大多数模型)
   - `n_positions` (GPT-2)
   - `max_seq_len` (MPT)
   - `seq_length` (ChatGLM2)
   - `model_max_length` (Command-R)
   - `max_target_positions` (Whisper)
   - `max_sequence_length`, `max_seq_length`, `seq_len`

2. **应用 RoPE Scaling**：对于使用 RoPE 的模型（如 LLaMA、Gemma），根据 `rope_parameters` 中的 `factor` 调整最大长度

3. **考虑滑动窗口**：如果启用 `--disable-sliding-window`，会使用滑动窗口大小作为最大长度

4. **默认值**：如果配置中找不到任何相关键，默认使用 **2048**

### ⚠️ 约束与验证

**当手动指定值超过模型推导值时**：
- 默认会**报错**，防止超出模型能力
- 可通过环境变量 `VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` 强制允许（**风险自负**）
- 超出限制可能导致：
  - **RoPE 模型**：产生 NaN 值
  - **绝对位置编码模型**：CUDA 数组越界错误

### 🔄 与其他参数的关系

```python
# 核心约束关系
max_num_batched_tokens ≤ max_num_seqs × max_model_len

# KV cache 容量
kv_cache_capacity = num_gpu_blocks × block_size

# 实际请求长度
request_length = prompt_length + output_length ≤ max_model_len
```

### 📊 典型值

| 模型 | 默认 max_model_len | 支持扩展 |
|------|-------------------|---------|
| Llama-2-7B | 4096 | 至 8192 |
| Llama-3-8B | 8192 | 至 128000 |
| Llama-3.1-8B | 128000 | 至 131072 |
| Mistral-7B | 32768 | 需自定义配置 |
| Qwen2-7B | 32768 | 至 131072 |
| Gemma-7B | 8192 | 至 8192 |

## 2. max-num-batched-tokens

### 📌 作用

**单次迭代（single iteration）中可以处理的 token 总数**。这是调度器进行批次决策时的关键预算约束。

### 🔧 配置方式

```bash
# 使用默认值（自动根据硬件选择）
vllm serve model_name

# 手动指定
vllm serve model_name --max-num-batched-tokens 16384

# 减小以降低延迟
vllm serve model_name --max-num-batched-tokens 2048
```

### 🎯 默认值计算

vLLM 根据 **GPU 类型**和**使用场景**自动设置：

| GPU 类型 | 内存 | Python API (LLM_CLASS) | API Server (OPENAI_API_SERVER) |
|---------|------|----------------------|---------------------------|
| 高端 GPU | ≥70GB | 16384 | 8192 |
| 普通 GPU | <70GB | 8192 | 2048 |
| TPU V6E | - | 2048 | 1024 |
| TPU V5E | - | 1024 | 512 |
| TPU V5P | - | 512 | 256 |
| CPU | - | 4096 × world_size | 2048 × world_size |

> **注**：高端 GPU 包括 H100、MI300x；普通 GPU 包括 A100、4090 等
>
> **性能提示**：根据 PR #17885，A100 上设置过大的 `max_num_batched_tokens` 反而会**降低吞吐量**

### ⚠️ 约束条件

```python
# 核心约束（自动验证）
max_num_batched_tokens ≤ max_num_seqs × max_model_len

# chunked prefill 禁用时
if not enable_chunked_prefill:
    max_num_batched_tokens = max(
        model_config.max_model_len,
        default_max_num_batched_tokens,
    )
```

### 🔄 与其他参数的关系

| 参数 | 控制维度 | 作用范围 |
|------|---------|---------|
| `max_model_len` | 单个请求 | 每个 sequence 的 prompt + output token 总数 |
| `max_num_batched_tokens` | 单次迭代 | 所有并行的 requests 在一次 forward pass 中的 token 总和 |
| `max_num_seqs` | 并发数 | 单次迭代最大请求数 |

**关系公式**：
```python
max_num_batched_tokens ≈ min(
    GPU_memory_budget,
    max_num_seqs × avg_request_length
)
```

### 📊 使用场景示例

#### 场景 1：多个短请求并发
```python
max_model_len = 4096           # 单个请求最长 4K tokens
max_num_batched_tokens = 8192  # 单次迭代最多 8K tokens
max_num_seqs = 128             # 最多 128 个并发请求

# ✅ 可同时处理：
# - 2 个请求，每个 4096 tokens (2 × 4096 = 8192)
# - 8 个请求，每个 1024 tokens (8 × 1024 = 8192)
# - 16 个请求，每个 512 tokens (16 × 512 = 8192)
```

#### 场景 2：长请求场景（使用 chunked prefill）
```python
max_model_len = 32768          # 支持 32K 上下文
max_num_batched_tokens = 8192  # 但单次只处理 8K tokens

# 一个 32K token 的请求会被拆分：
# - 第一次迭代：处理 8192 tokens
# - 第二次迭代：处理 8192 tokens
# - 第三次迭代：处理 8192 tokens
# - 第四次迭代：处理 7192 tokens
```

### 🎛️ 调优建议

#### **何时增大**（提高吞吐量）
- ✅ GPU 内存充足
- ✅ 请求主要是短 prompt
- ✅ 追求更高吞吐而非低延迟
- ✅ H100/A100 等高端 GPU

#### **何时减小**（降低延迟/内存占用）
- ✅ GPU 内存受限
- ✅ 请求主要是长 prompt
- ✅ 追求低延迟（每次迭代快）
- ✅ 多个共享 GPU 的实例

## 3. KV Cache 相关参数

### 📌 核心参数概览

| 参数 | 作用 | 默认值 | 影响 |
|------|------|-------|------|
| `--gpu-memory-utilization` | GPU 内存利用率 | 0.9 | **直接影响 KV cache 大小** |
| `--block-size` | Block token 数 | 自动选择（16） | 管理粒度，间接影响利用率 |
| `--cache-dtype` | KV 数据类型 | auto | **直接占用内存（50%差异）** |
| `--kv-cache-memory-bytes` | 直接指定 KV 大小 | None | **精确控制（优先级最高）** |

### 🧮 KV Cache 内存计算

#### **核心公式**

```python
# 单个 KV cache block 的内存大小（字节）
page_size_bytes = 2 × block_size × num_kv_heads × head_size × dtype_size

# 完整计算公式
KV_cache_memory = num_layers × num_blocks × 2 × block_size × num_kv_heads × head_size × dtype_size
                 └─────┬─────┘   └────┬────┘   └──────────────┬──────────────┘
                   层数          块数量          单块内存（2 = K + V）
```

#### **实际计算示例：Llama-3-8B on A100 (40GB)**

```python
# 模型配置
num_layers = 32
num_kv_heads = 8         # GQA
head_size = 128
cache_dtype = bfloat16   # 2 bytes

# KV cache 配置
block_size = 16
gpu_memory_utilization = 0.9
GPU_total_memory = 40 GB

# 假设模型权重占用 16 GB，剩余 24 GB
available_for_kv = 24 GB

# 单块内存
page_size_bytes = 2 × 16 × 8 × 128 × 2 = 65,536 bytes = 64 KB

# 所有层的单块内存
single_block_all_layers = 32 × 64 KB = 2,048 KB = 2 MB

# 可分配的 block 数量
num_gpu_blocks = 24 GB / 2 MB = 12,288 blocks

# KV cache 总容量
kv_cache_capacity = 12,288 × 16 = 196,608 tokens
```

### 🔧 可调整参数详解

#### **1. gpu-memory-utilization**

```bash
vllm serve model --gpu-memory-utilization 0.95
```

- **作用**：控制 GPU 内存利用率（0.0-1.0）
- **影响**：直接影响 KV cache 可用内存
- **注意**：需要为模型权重、NCCL 通信等留出足够空间

#### **2. block-size**

```bash
vllm serve model --block-size 32
```

- **可选值**：1, 8, 16, 32, 64, 128, 256
- **影响**：
  - **越大**：内存利用率高，但灵活性降低
  - **越小**：灵活分配，但管理开销增加
- **自动选择**：vLLM 会根据平台和模型自动选择最优值

#### **3. cache-dtype**

```bash
vllm serve model --cache-dtype fp8
```

- **可选值**：
  - `"auto"`：使用模型 dtype
  - `"fp8"`, `"fp8_e4m3"`：8位浮点（节省 50% 内存）
  - `"bfloat16"`：16位浮点
- **节省效果**：FP8 相比 BF16/FP16 可节省 **50% KV cache 内存**

#### **4. kv-cache-memory-bytes（最精确）**

```bash
vllm serve model --kv-cache-memory-bytes 21474836480  # 20 GB
```

- **优先级**：**最高**，指定后会忽略 `gpu_memory_utilization`
- **适用场景**：需要精确控制 KV cache 大小

### 🔄 KV Cache 与其他参数的关系

```python
# 内存分配
total_gpu_memory = model_weights + kv_cache + workspace

# KV cache 容量
kv_cache_capacity = num_gpu_blocks × block_size

# 单请求可分配
max_tokens_per_request = max_model_len

# 并发能力
max_concurrent_requests ≈ kv_cache_capacity / avg_request_length
```

### 📊 优化建议

#### **场景 1：长上下文模型**
```bash
vllm serve model \
    --max-model-len 128000 \
    --gpu-memory-utilization 0.95 \
    --cache-dtype fp8 \
    --block-size 16
```

#### **场景 2：高吞吐短请求**
```bash
vllm serve model \
    --max-num-batched-tokens 16384 \
    --gpu-memory-utilization 0.9 \
    --block-size 32
```

#### **场景 3：内存受限环境**
```bash
vllm serve model \
    --gpu-memory-utilization 0.7 \
    --cache-dtype fp8 \
    --kv-cache-memory-bytes 10737418240  # 10 GB
```

## 4. 参数关系总结

### 🎯 核心约束关系

```python
# 1. 批次约束
max_num_batched_tokens ≤ max_num_seqs × max_model_len

# 2. 内存约束
kv_cache_memory ≤ (gpu_memory_utilization × total_memory) - model_weights

# 3. 容量约束
kv_cache_capacity = num_gpu_blocks × block_size

# 4. 实际可用
actual_max_requests = min(
    max_num_seqs,
    kv_cache_capacity // avg_request_length
)
```

### 📊 参数影响矩阵

| 参数 | 影响内存 | 影响延迟 | 影响吞吐 | 推荐调整场景 |
|------|---------|---------|---------|-------------|
| `max-model-len` | ⬆️ | ➡️ | ➡️ | 镀要处理长文档 |
| `max-num-batched-tokens` | ➡️ | ⬆️ | ⬆️ | 调整吞吐-延迟平衡 |
| `gpu-memory-utilization` | ⬆️ | ➡️ | ➡️ | GPU 独占使用 |
| `block-size` | ➡️ | ⬆️ | ⬆️ | 根据请求长度分布 |
| `cache-dtype` | ⬇️ (FP8) | ➡️ | ➡️ | 内存受限时 |
